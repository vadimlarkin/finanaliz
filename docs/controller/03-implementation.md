# Тикет 03. Интерфейс и контрольные примеры

Исполнитель Transfer watson. База `c0049205be1140e34439afa637b639d199b90224`. Запись создана до первого теста. CLI и выходные артефакты разрешены поручением пользователя.

Публичный интерфейс: `match_own_transfers.py INPUT.json OUTPUT.json`, вход `local-own-transfers-1.0` с `cashflow` формата задачи 01, необязательными `external_accounts` с подтверждёнными account/owner_id и `decisions`. Каждое решение confirm/reject содержит pair_id, два operation_ids, fingerprints исходных реквизитов, reason и evidence.sources. Для разных дат дополнительно нужны совпадающие document_number и operation_date обеих операций и решения. Подтверждение не выводится из суммы и близости дат.

Результат содержит кандидатов, подтверждённые пары, нерешённые совпадения, переводы вне охвата, решения, исходные данные и cashflow_input для повторного расчёта через calculate_cashflow. Коды 0 при отсутствии нерешённых связей и ошибок, 2 при диагностике или ограничении очистки. Нерешённые операции не исключаются. Исходный JSON не меняется, результат записывается атомарно. Суммы рассчитываются существующим Decimal-расчётом.

Сохранённое подтверждение передаётся в дополнительном CSV-столбце `transfer_confirmation` как JSON. Оно содержит pair_id, operation_ids, fingerprints, owner_id, accounts, reason и evidence. check_cashflow проверяет привязку к строкам и реквизитам. Старые корректные пары одной даты без этого поля остаются совместимыми. Подтверждение новых пар выполняет аналитик; автоматический алгоритм только предлагает кандидатов.

SHA256 операции вычисляется по исходным непустым полям, даты приводятся к ISO с исключением category, category_status, pair_id и transfer_confirmation. Эти поля меняет аналитик при подтверждении; источники, даты, суммы, счета и банковские реквизиты входят в снимок. Применение сохранённого решения после изменения значимого реквизита останавливается диагностикой.

Независимый пример: собственный перевод 100.01 со счёта A 31 января и поступление 100.01 на B 1 февраля. В январе также списание поставщику 20.02, в феврале выручка 50.03. Исходные обороты: списания 120.03, поступления 150.04; после подтверждённой пары остаются 20.02 и 50.03. Январский очищенный дебет 20.02, февральский очищенный кредит 50.03. Исходные даты и банковские обороты сохраняются. Равные суммы без подтверждения остаются в расчёте.

TDD ведётся по одному наблюдаемому поведению через CLI и выходные JSON/CSV. Сценарии поведения агента описываются отдельно; модельные прогоны не заявляются. Макеты и генераторы PDF не меняются.

## Ограничения

Поддержка разных дат требует совпадающих номера документа и даты операции на обеих сторонах. Произвольный способ доказательства связи первая версия не угадывает. Владельцы и источники уже проверены аналитиком; программа проверяет согласованность подготовленных данных. Непредставленные счета не становятся обязательной новой частью исследования. Старые пары одной даты сохраняют прежний CSV-контракт; wrapper дополнительно сверяет представленный реестр владельцев.

При коде 2 нерешённые операции остаются в обороте, а полный очищенный результат не готов. Выход расчёта сохраняет явные ограничения, полный свободный денежный поток не определяется.
