# Тикет 08. Интерфейс до первого теста

Исполнитель Run dmc. База `9f7e38e03d14b2d47aaff37a13dcbc8a86e91505`. Пользователь разрешил CLI и выходные артефакты. Запись создана до первого теста.

CLI: `run_local_analysis.py CASE.json WORKDIR`. Схема `local-analysis-runner-1.0`: case_id, mode corporate/ip, borrower name/inn, assessment_date, scope, sources, необязательные intake/report_input/source_files, обязательные steps и явный render_pdf. Пути входов относительно CASE.json. Источники с одинаковым ID должны иметь одинаковое происхождение. Рабочий каталог отделён от всех входных файлов.

Корпоративный intake содержит reviewed_by и checks по шести пунктам borrower, loan, annual_statements, trial_balance, debt, statements. Каждый пункт имеет status confirmed/missing/conflicting, sources; неподтверждённый пункт содержит конкретные borrower_request и/или creditor_question. Отсутствующий пункт также блокирует. Проверка комплектности является результатом аналитика, названия файлов её не устанавливают. Остановка предшествует чтению финансовых входов и расчётам. Сохраняются intake.md и раздельные тексты запросов, финансовые outputs отсутствуют.

Выбранные steps: cashflow с input стандартного реестра01 и/или imports path/profile, overlaps с loads/decisions, transfers с external_accounts/decisions; debt_register и loan_schedule с путями JSON; pdf_extractions со списком path и параметров. Этапы вызывают готовые функции. При наличии report_input создаётся расчёт существующей формы; render_pdf true требует этот вход. Для ИП неизвестные условия займа и неполный охват не делают ненужный этап обязательным.

WORKDIR/current публикуется только после успешных выбранных стадий и проверок. Предыдущий комплект переносится в backups. Ошибка сохраняет current без изменения и пишет отдельный attempt.json с этапом/причиной. Версии case, реально прочитанных входов, параметров и программ сохраняются в manifest и snapshots. Повторный запуск заново вычисляет зависимые стадии. PDF имеет page_count=1 и visual_review required/pending, осмотр аналитика не предполагается.

Независимые контрольные примеры: готовый корпоративный examples/investor.json даёт действующий макет2.2 после явного intake; отсутствие обязательной ОСВ и неизвестные комиссии дают раздельные запросы и не создают analysis/PDF. Ограниченный ИП с неизвестным сроком сохраняет loan term null и получает макет3.2. Готовые реестры01/02/03 дают проверенные 150.47/22.06 либо очищенные20.02/50.03, новая несвязанная выручка меняет только соответствующий итог. Неизменённая пара сохраняет применимость решения, изменённый реквизит требует повторного подтверждения. Ошибка после успеха не меняет байты current; исправление создаёт новый current и backup.

TDD ведётся по одному CLI-поведению. Детерминированные тесты и сценарии чтения инструкции учитываются отдельно от визуального осмотра и модельных прогонов. Общие расчётные формулы, макеты, SKILL.md и установка не меняются.

### Сценарии чтения инструкции

Проверены чтением отдельно от CLI-тестов: подходящий запрос «собрать выбранные локальные расчёты из подготовленных JSON» ведёт к reference; похожий запрос «проверить достоверность документов и решить выдать заём» не поручает runner такую проверку; неполный корпоративный intake ведёт к остановке/аналитику, а неизвестный срок ИП — к ограниченному разбору. ## Исправление после независимой приёмки

База исправления `dda98b264ad13a7844d31372da21b4ad91d86862`, история не переписывалась. Spec inspector воспроизвёл P2: сохранённые transfer_confirmation готового реестра не попадали в runner_decision_contexts при пустых новых decisions. Изменение выбранного отдельного файла-основания ошибочно позволяло повторно использовать подтверждённую пару. Новый CLI-тест сначала получил ошибочный code0 вместо ожидаемого code2.

Содержательная подпись не включает производный owner_id; актуальные владельцы, fingerprints строк, релевантные источники и SHA выбранных байтов входят в проверяемый контекст. Общий matcher не менялся. Исправлено также описание: steps обязателен, хотя может быть пустым объектом.
