# Один локальный запуск выбранных этапов

Используй `scripts/run_local_analysis.py CASE.json WORKDIR`, когда поручение требует согласованный комплект из уже подготовленных данных и выбранных локальных расчётов. Скрипт работает без сети. Финансовые формулы и формы отчёта выполняют существующие модули. Решение о финансировании остаётся кредитору.

```bash
python skills/borrower-financial-analysis/scripts/run_local_analysis.py examples/local-analysis-corporate.json work/local-corporate
python skills/borrower-financial-analysis/scripts/run_local_analysis.py examples/local-analysis-ip.json work/local-ip
```

Оба примера вымышленные. Первый использует учебное подтверждение минимума; это не свидетельство проверки реальных документов. Второй показывает ограниченный разбор ИП при неизвестном сроке нового займа.

## Поручение и входы

CASE — JSON со `schema_version: "local-analysis-runner-1.0"`. Обязательные поля:

| Поле | Содержание |
| --- | --- |
| `case_id` | Непустой идентификатор проверки |
| `mode` | `corporate` для компании или ИП с бухучётом; `ip` для ИП без бухучёта |
| `borrower` | Объект с `name` и строкой `inn`; для ИП 12 цифр |
| `assessment_date` | Дата проверки `YYYY-MM-DD` |
| `scope` | Явный предмет поручения и пределы разбора |
| `sources` | Массив источников `id`, `file`, `locator` |
| `render_pdf` | Логическое значение; PDF требует `report_input` |
| `steps` | Объект выбранных этапов; пустой объект разрешён для готовой формы |

Необязательные поля: `intake`, `report_input` (путь готовой формы), `source_files` (пути дополнительных исходников для фиксации версии). Имена, даты и порядок готовой формы должны совпадать с CASE; форма ИП также содержит тот же ИНН. Фактические банковские периоды и дата реестра долгов не могут быть позже даты проверки. Плановый график нового займа может относиться к будущему.

Пути настроек и выбранных входов разрешаются относительно CASE. `file` внутри описателя источника разрешается относительно JSON, где описатель объявлен. Описатели сохраняются без изменения: случайный путь подготовки результата не меняет fingerprints. Один ID с разным происхождением вызывает ошибку. Для воспроизведения отдельно выбери фактически используемые документы в `source_files`, если их не читает выбранный этап. Само упоминание документа не означает, что программа прочитала его или проверила достоверность.

Все входы, конфигурации и объявленные исходники должны находиться вне WORKDIR. Скрипт отказывает при пересечении с управляемыми путями и не перезаписывает исходники. Выбранные байты сохраняются в snapshots; заявленные `source.sha256` и `loads.sha256` сверяются с фактически выбранной версией. При изменении CSV/PDF между фиксацией версии и чтением модулем попытка останавливается.

## Подтверждение обязательного минимума

Для `corporate` передай `intake.reviewed_by` и массив `checks` по шести пунктам: `borrower`, `loan`, `annual_statements`, `trial_balance`, `debt`, `statements`. Каждый check содержит `id`, `status` (`confirmed`, `missing`, `conflicting`), массив `sources` с ID из CASE. Подтверждение требует непустых действующих ссылок. Минимум и календарные периоды определяются действующим [intake.md](intake.md); машинный статус передаёт результат работы аналитика, а не заменяет её.

Пример конкретного пробела:

```json
{"id":"statements","status":"missing","sources":["BANK"],"borrower_request":"Просим выписку по счёту 40702810000000000001 за сентябрь 2026 года; январь–август уже получены."}
```

Неполный минимум останавливает запуск до финансовых расчётов и PDF. `borrower_request` передаёт только подтверждённый пробел и оставшийся период, `creditor_question` — отдельный вопрос кредитору. Условия нового займа адресуются кредитору. Отсутствующий intake/check означает непереданную аналитическую проверку: программа просит уточнить её у аналитика и не придумывает сообщение заёмщику. Причины и точные запросы сохраняются в `intake.md`, сообщения — раздельно.

Для `ip` этот минимум не требуется. Отсутствие бухформ, неполный охват и неизвестные условия ограничивают зависимую часть, независимый выбранный разбор продолжается. Не заказывай ненужные этапы для заполнения интерфейса.

## Выбор этапов

| Настройка `steps` | Действие |
| --- | --- |
| `cashflow.input` | Путь подготовленного реестра `local-cashflow-1.0` |
| `cashflow.imports` | Список `{path, profile}` для существующего CSV-импорта |
| `cashflow.overlaps` | `{loads, decisions}` для сверки пересечений; импортированные loads добавляются автоматически |
| `cashflow.transfers` | `{external_accounts, decisions}` для сопоставления собственных переводов |
| `debt_register` | Путь JSON существующего модуля обязательств; `borrower_id` равен ИНН CASE |
| `loan_schedule` | Путь JSON существующего расчёта графика |
| `pdf_extractions` | Список `{path, language, ocr}` с необязательными `dpi`, `min_text_chars` |

При нескольких импортах передай общий `cashflow.input` с явными периодом, счетами, охватом и общими независимыми банковскими контролями. Скрипт не придумывает общие контрольные итоги из отдельных выписок. Профили и решения используют контракты [импорта](local-statement-csv.md), [пересечений](local-statement-overlaps.md) и [переводов](local-own-transfers.md).

Последовательность: импорт → пересечения → сопоставление переводов → расчёт потока. После пересечений matcher получает очищенный registry, расчёт — его cashflow_input. Ошибки аудита останавливают публикацию. Каждый повтор начинается с выбранных исходных строк; прежние промежуточные расчёты не используются.

Старые решения проверяются по fingerprints операций и релевантному контексту владельцев, источников и выбранной версии отдельного документа-основания. Несвязанная новая выписка прежнюю пару не отменяет. При изменении контекста аналитик повторно сверяет пару, обновляет fingerprints и содержательное `reason` с новым основанием. Перестановка ключей или пробелы повторной сверкой не считаются. На первом запуске явное решение аналитика является исходным подтверждением. Контекст охватывает также готовые `transfer_confirmation` обеих строк и legacy same-day пары, даже при пустом `transfers.decisions`. Для повторной сверки готовой пары передай заново подготовленный matcher реестр с актуальными fingerprints и новым содержательным `reason` в одинаковом подтверждении обеих сторон. Если изменились строки или владелец, сначала сними прежние pair_id/transfer_confirmation обеих сторон, восстанови категории own_out/own_in и явно подтверди пару новым решением matcher по текущим данным. Одного изменения оформления JSON недостаточно.

Числовые patches сохраняют неизвестное как `null`, заменяя старые значения; BKI-часть ИП заменяется целиком. Корпоративный patch графика применяется отдельно от инвесторских условий ИП: комиссия не подменяет ставку. Скрипт не сочиняет текстовые выводы. Аналитик готовит их в форме и проверяет после изменения расчётных данных.

## Результаты и продолжение

Успех возвращает JSON `status: success`, код 0. В `WORKDIR/current` находятся выбранные стадии, snapshots, `manifest.json` и, если выбрана форма, `input.json`, `analysis.json`, `report.pdf`. Manifest фиксирует заёмщика, предмет, дату, реальные входы, профили, решения, SHA256 программ, версии среды и хеши артефактов. Относительные ссылки читаются от корня комплекта; кэш извлечения остаётся в WORKDIR/cache.

Публикация выполняется переносом полностью подготовленного дерева на той же файловой системе. Предыдущий current остаётся в `backups`; при ошибке публикации он возвращается. Ошибка любого выбранного этапа возвращает код 2, конкретный stage и причину, сохраняет прежний current и отдельную попытку в `attempts` плюс `attempt.json`. Остановка по intake имеет `status: stopped`; расчётов и PDF в попытке нет. Повреждённые или пересекающиеся пути могут быть отклонены до записи попытки, чтобы сохранить исходники.

PDF создают действующие корпоративный макет 2.2 и макет ИП 3.2. Автоматическая проверка одной страницы не является осмотром. Manifest оставляет `visual_review: pending`, `visual_review_required: true`. Перед передачей проверь страницу, числа, подписи, источники и терминологию; осмотр фиксируй отдельно. Детерминированные тесты скрипта, сценарии чтения инструкции и модельные прогоны учитываются отдельно.
