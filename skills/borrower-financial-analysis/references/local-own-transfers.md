# Проверка собственных переводов

Применяй после подтверждения владельцев счетов и подготовки реестра `local-cashflow-1.0`. Скрипт предлагает связи и применяет сохранённое решение аналитика. Он не устанавливает владельца по назначению платежа и не подтверждает документы.

```sh
python <skill-dir>/scripts/match_own_transfers.py <work-dir>/transfers-input.json <work-dir>/transfers-result.json
```

Код 0 означает отсутствие нерешённых связей и ошибок расчётного аудита в заявленном охвате. Код 2 означает диагностику либо оставшиеся нерешённые связи. Исходник сохраняется, результат записывается атомарно в отдельный файл. Работа локальная. Одинаковый вход даёт одинаковые байты JSON. Отсутствие банковских контролей сохраняется в расчёте явно.

## Подготовь вход

Корневой объект имеет `schema_version: local-own-transfers-1.0` и `cashflow` по [local-cashflow.md](local-cashflow.md). `accounts` внутри cashflow содержит представленные счета с уже подтверждёнными `owner_id`. В операции могут быть `counterparty_account`, `document_number`, `operation_date`. Исходная дата проводки сохраняется в `date`, дата общей операции отдельно в `operation_date`.

Необязательный `external_accounts` перечисляет подтверждённые счета вне представленного охвата как `account` и `owner_id`. Идентификаторы уникальны и не совпадают с представленными счетами. Только совпадающий подтверждённый владелец позволяет отнести такой перевод к `own_out` либо `own_in`. Обе категории остаются в обороте. Счёт другого владельца не становится собственным. Наличие внешнего счёта не расширяет предмет исследования автоматически.

Кандидат требует разных представленных счетов одного владельца, равной суммы противоположных операций и согласованных встречных счетов. Даты могут различаться. Алгоритм не подтверждает пару по близости дат или сумме. В `candidates` доступны ID, даты, сумма и SHA256 снимков. Если одной стороне подходят несколько операций, связь остаётся нерешённой до решения аналитика. Оставшаяся третья операция не исчезает после выбора одной пары. Сторона собственного перевода без встречной операции отмечается `incomplete_pair`.

## Подтверди связь

`decisions` является массивом решений. Для каждой пары передай:

- `pair_id`, непустой уникальный идентификатор пары.
- `operation_ids`, два различных ID исходных операций.
- `action`, `confirm` либо `reject`. Reject отклоняет предложенную связь; неподтверждённые стороны могут остаться неполными собственными переводами.
- `fingerprints`, объект ID операции → SHA256 из результата кандидатов.
- `reason`, основание решения по оригиналам.
- `evidence.sources`, непустой массив ID объявленных источников.

Для подтверждения разных дат в evidence дополнительно обязательны `document_number` и `operation_date`. Они должны совпадать с соответствующими реквизитами обеих операций. Разница дат проводки остаётся в исходных строках. Первая версия поддерживает именно такой способ связи; другие способы требуют отдельного подтверждаемого контракта.

Снимок операции включает исходные непустые поля, кроме изменяемых аналитиком `category`, `category_status`, `pair_id`, `transfer_confirmation`. Даты `date` и `operation_date` канонизируются в ISO. Пустые CSV-ячейки эквивалентны отсутствующим полям. Суммы, счета, источники, строки и прочие реквизиты входят в SHA256. Изменение этих значений делает прежнее решение устаревшим. Скрипт выдаёт `stale_decision`, не подгоняет решение под новые операции.

Операция не может входить в два новых подтверждения. Конфликтующие подтверждения и повторные решения по одной паре отклоняются целиком. Решение не выбирается по порядку массива. После исправления решения повтори запуск на исходном реестре. Старые корректные пары одной даты с `pair_id` и подтверждёнными категориями сохраняются; уже подтверждённую пару не нужно подтверждать вторым решением.

## Передай результат расчёту и CSV-аудиту

`confirmed_pairs` раскрывает принятые пары. `unresolved` и `issues` содержат оставшиеся вопросы; при коде 2 полный очищенный результат не готов. `outside_transfers` сохраняет отдельные операции между своим представленным и своим непредставленным счётом. `cashflow_input` содержит реестр с аннотациями подтверждённых пар, `calculation` результат действующего calculate_cashflow, включая месяцы, исходные обороты и обороты после исключения пар. Основной долг, проценты и комиссии сохраняют существующие правила расчёта.

В подтверждённых строках добавляется `transfer_confirmation`. Для CSV это строка JSON, одинаковая на обеих сторонах. Она содержит pair_id, operation_ids, fingerprints, owner_id, accounts, reason и evidence. Записывай её стандартным CSV writer, чтобы сохранить кавычки. Не сокращай JSON и не переноси подтверждение на изменённые строки.

Действующий [cashflow-audit.md](cashflow-audit.md) проверяет обе стороны и подтверждение. Для разных дат без сохранённого подтверждения он возвращает ошибку. Подтверждение одной даты также проверяется, если поле передано. Прежние корректные пары одной даты без этого поля продолжают проходить. В аудите `transfer_evidence` раскрывает basis, даты и основание. Самостоятельная CSV-проверка проверяет заявленное подтверждение; владельцев сверяет аналитик и wrapper по реестру счетов.

После подтверждения 100.01 списания и 100.01 поступления исключаются по одному разу. В контрольном примере остаются списания 20.02 и поступления 50.03, при исходных оборотах 120.03 и 150.04. Январская и февральская даты сохраняются. Очищенный остаток не объявляется полным внешним или свободным денежным потоком: собственные переводы за пределы охвата остаются внутри него.

Макеты PDF и генераторы не меняются. Этот этап сам PDF не создаёт. Если итоговый анализ выпускает PDF, действуют его обычные арифметические, терминологические и визуальные проверки.

## Сценарии поведения агента

Это проверки инструкции чтением. Отдельный модельный прогон не проводился.

- Подходящий запрос: сверить переводы между двумя представленными счетами одного ИП. Агент подтверждает владельцев, получает кандидатов, сверяет документ и обе даты, сохраняет решение и повторяет расчёт.
- Похожий запрос вне области: признать перевод учредителю собственным по назначению платежа. Агент не подменяет владельца счёта назначением, устанавливает роль операции отдельно.
- Неполная пара: списание на подтверждённый свой счёт есть, встречная выписка не представлена. Агент сохраняет own_out в обороте и ограничение охвата, не исключает одну сторону.
- Противоречие: одной операции назначены две пары либо изменён источник после решения. Агент сохраняет диагностику, сверяет оригиналы и исправляет подготовленное решение. Нерешённое совпадение не становится подтверждённой парой.
