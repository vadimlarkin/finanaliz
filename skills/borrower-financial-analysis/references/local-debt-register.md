# Локальный свод проверенного реестра обязательств

Прочитай перед арифметикой по уже проверенным договорам из БКИ и других документов. Скрипт не читает произвольный отчёт ОКБ, не определяет достоверность источников и не принимает решение о финансировании.

```sh
python <skill-dir>/scripts/summarize_debt_register.py <work-dir>/debt-register.json <work-dir>/debt-summary.json
```

Код 0 означает, что свод построен без противоречий идентичности, дат и сумм. Частичные и неизвестные суммы допустимы и обозначены явно. Код 2 означает ошибку входа, нерешённое совпадение или противоречие. При структурной ошибке результат содержит `issues` с кодом `invalid_input`. При содержательном противоречии результат сохраняет доступную расшифровку, но зависимые полные суммы остаются null. Исходный JSON читается без изменения. Результат записывается атомарно в отдельный файл; путь и жёсткая ссылка на исходник запрещены.

## Подготовь вход

Схема `local-debt-register-1.0`. Корневые поля:

- `borrower_id`: проверенный идентификатор исследуемого заёмщика.
- `report_date`: дата комплекта реестра, ГГГГ-ММ-ДД. Даты исходных записей и регулярных ориентиров не могут быть позже неё. Она не становится общей датой остатка.
- `kind`: `bki` только если аналитик подтвердил, что реестр прямых обязательств относится к БКИ с указанной датой отчёта. Значение `verified_register` по умолчанию сохраняет общий свод, но не заполняет карточки БКИ по договорным и смешанным источникам.
- `sources`: массив уникальных объектов `id`, `file`, `locator`, необязательный `kind`. Все ссылки записей, решений и платежей должны указывать на эти идентификаторы.
- `records`: массив записей; пустой массив даёт неизвестные суммы, отсутствие реестра не считается нулевым долгом.
- `decisions`: необязательные явные решения аналитика о совпадениях.

Одна запись:

```json
{
  "id": "A-20261020",
  "contract_id": "VERIFIED-UID-A",
  "subject_id": "BORROWER",
  "role": "borrower",
  "creditor_id": "BANK-A",
  "status": "active",
  "as_of": "2026-10-20",
  "sources": ["BKI"],
  "amounts": {
    "principal": "100.01",
    "interest": "2.02",
    "total": "102.03",
    "overdue": "0.00",
    "limit": null
  },
  "monthly_payment": {
    "amount": "10.01",
    "as_of": "2026-10-20",
    "frequency": "monthly",
    "sources": ["BKI"]
  },
  "payments": [
    {
      "id": "PAYMENT-1",
      "date": "2026-12-15",
      "amount": "40.04",
      "treatment": "replace",
      "sources": ["BKI"]
    }
  ],
  "maturity": {"date": "9999-12-31", "confirmed": false}
}
```

Суммы в рублях, неотрицательны, с точностью до копейки. Допустимы JSON-числа и десятичные строки с точкой. Для денег арифметика выполняется через Decimal. Неизвестное обозначай null или отсутствующим компонентом в `amounts`, не заменяй нулём. `principal` означает основной долг, `total` общую задолженность, `interest` начисленные проценты, `overdue` просроченную задолженность, `limit` лимит. Лимит не прибавляется к долгу. Общая задолженность может содержать иные расходы, поэтому скрипт не достраивает её из двух компонентов.

`id` уникален среди записей. `contract_id` уже проверен аналитиком, скрипт не восстанавливает его по названию кредитора. `role`: `borrower`, `guarantor` или `other`. `status`: `active`, `closed` или `unknown`. Поручительства исследуемого лица и прямые долги других лиц сохраняются отдельно от прямого долга заёмщика.

`as_of` может быть null. Недатированные нули без платёжных сведений сохраняются среди проигнорированных технических записей. Недатированная содержательная запись вызывает диагностику. Она не отменяет датированный остаток. По одному проверенному договору выбирается последняя датированная запись; более старые идентификаторы сохраняются. Разные содержательные записи на последнюю дату требуют сверки. Исправь проверенный вход по оригиналу и запусти повторно. Статус unknown и положительный долг при статусе closed также требуют решения.

## Реши совпадения

Разные проверенные идентификаторы с одним кредитором автоматически не объединяются. Скрипт консервативно перечисляет такие пары в `unresolved_matches`, исключает их из подтверждённого полного итога и ждёт решения аналитика. Явно разные договоры можно сохранить решением `separate`; подтверждённые отражения одного договора объединить решением `merge`:

```json
{
  "contracts": ["VERIFIED-UID-A", "ALIAS-A"],
  "action": "merge",
  "reason": "Один УИд подтверждён на двух страницах",
  "sources": ["BKI"]
}
```

Каждое решение содержит ровно два разных известных прямых договора, действие, непустое основание и источники. Цепочки merge поддерживаются. Противоречащие решения merge и separate отклоняются. Повторный неизменённый вход даёт одинаковые байты результата. После изменения реестра аналитик повторно сверяет применимость решений по оригиналам; скрипт не подтверждает их актуальность вместо него.

## Прочитай результат

`contracts` раскрывает принятые записи, все идентификаторы обновлений, технические записи, подтверждённый срок и ошибки договора. `other_roles` содержит записи иных ролей и субъектов. `totals` отдельно показывает каждый компонент, полное `value`, `known_subtotal`, договоры и записи слагаемых, их даты и источники. Неполный подытог нельзя выдавать за полный долг. Общая сумма не рассчитывается подстановкой основного долга вместо общей задолженности.

`record_period` содержит даты последних активных записей, `source_record_period` диапазон всех датированных исходных записей. `basis` равен `sum_of_latest_records`, `common_balance_date` остаётся null. Совпадение дат нескольких записей само по себе не подтверждает сверку всего долга на эту дату.

`payment_guide.regular_monthly` содержит полное значение только при известном месячном ориентире каждого активного договора, а также известный подытог, охват и датированные записи. `includes_dated_payments: false` означает, что эта база не содержит отдельно раскрытых событий. `dated_payments` сохраняет суммы, даты, периодичность исходной базы, источники и правило учёта относительно неё. `replace` заменяет базу договора в своём месяце, `additional` добавляется сверх неё, `unknown` требует решения. Скрипт не выводит неизвестный основной долг финального платежа из других компонентов.

`monthly_payment.frequency` принимает monthly, quarterly, annual или unknown. Только датированный monthly с известной суммой передаётся в месячную базу формы. Другие частоты сохраняются в принятых записях и остаются неизвестными для этого расчёта. Общая дата окончания договора и техническая дата не становятся `monthly_until`. Даже подтверждённый срок погашения сам по себе не доказывает исполнение.

## Заполни действующую форму ИП

`pdf_patch` содержит `sources`, `bki` и `credit_load.contracts`. Объедини источники по id с остальным проверенным входом. Замени только соответствующие числовые поля, сохрани предмет исследования, тексты и условия нового займа. Конфликт одного id источника с разным содержанием требует сверки.

`bki` формируется только для kind bki, с датой отчёта и диапазоном принятых записей. Основной долг, общая задолженность и просрочка передаются отдельно. Если общая задолженность содержит иные расходы, необязательное поле процентов не передаётся в проверку разложения формы, а точный компонент остаётся в своде. Частичные суммы передаются как missing/null. Договорный свод вида verified_register не становится карточкой БКИ.

`credit_load.contracts` совместим с [ip-credit-load.md](ip-credit-load.md). Начало и срок сценария задаются по текущему займу отдельно. Если правило хотя бы одного отдельного платежа неизвестно, регулярная база этого договора в вставке остаётся неизвестной, его датированные платежи не передаются в числовую вставку. Это сохраняет неизвестность в действующем расчёте формы. При неизвестной, недатированной или немесячной базе дополнительный платёж также не передаётся как полный итог месяца. Известный replace при неизвестной базе допустим; дополнительные платежи того же месяца могут учитываться вместе с явной заменой. Исходные события, суммы и даты остаются в `payment_guide.dated_payments`, а причины удержания и идентификаторы событий находятся в `payment_guide.patch_limitations`. Эти суммы остаются доступными для разбора аналитиком. Точный будущий график скрипт не обещает. Не выводи подтверждённое отсутствие платежей из такой вставки.

В расчётном результате деньги сохраняются десятичными строками. Для существующей формы числовые поля вставки преобразуются в JSON-числа только при сохранении десятичного значения. Если такое преобразование теряет точность, поле остаётся missing/null; точная сумма остаётся в своде. Макет ИП 3.2 и корпоративный макет 2.2 сохраняются.

## Сценарии поведения агента

Это проверки чтением инструкции, не проведённые модельные прогоны.

- Подходящий запрос: «Сведи проверенный реестр прямых обязательств ИП». Агент связывает записи и роли, запускает CLI, сверяет состав принятых договоров и суммы по оригиналам, затем переносит допустимые числа в действующую форму.
- Похожий запрос вне области: «Распознай любой отчёт ОКБ и автоматически подтверди отсутствие других долгов». Этот скрипт не выполняет такое поручение. Сначала нужен проверенный реестр и установленный охват.
- Неполные данные: один кредитор с двумя неразрешёнными УИд, неизвестный месячный платёж или недатированное обновление. Агент сохраняет отдельные договоры и известный подытог, объясняет конкретную неопределённость, получает решение аналитика и повторяет расчёт. Неполноту не скрывает нулём и не объявляет точный будущий график.
